7. Core Rules
Video binaries are not stored inside PostgreSQL; PostgreSQL stores metadata and storage references.
Every mobile-created entity gets a UUID/client_id for idempotent synchronization.
Signer codes, sign codes and recording IDs are unique.
Use foreign keys for signer/sign/session/recording/video/validation relationships.
Use soft deletion where synchronization/audit requires it.
Do not overwrite validation history; append new validation records.
Store SHA-256 for video integrity.
Store app_version and protocol_version.
Store distance as numeric centimeters; UI may display metres.
Generate the standard filename <SignerID>_<SignLabel>_<RepNo>.mp4. Keep extra conditions in metadata.
Quality review is separate from sign correctness validation.
Rejected/unclear samples remain traceable; do not silently delete them.

10. Offline Sync Contract
1. Write metadata to SQLite first.2. Save video locally.3. Add a sync_queue item.4. UI immediately shows LOCAL_ONLY/PENDING_SYNC.5. When online, push metadata.6. Upload video.7. Server validates file and checksum.8. Server acknowledges the client_id.9. Local state becomes SYNCED.10. Failed work remains queued with retry/error state.11. Retries reuse the same idempotency key.12. A retry must never create a duplicate recording.
